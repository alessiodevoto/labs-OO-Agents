## What We Learned

### Lesson 1: More Changes ≠ Better

**opt3 → opt11 journey** (8 iterations, NO improvement):
- Each change seemed logical
- But we moved AWAY from the correct approach
- opt11's "entity filtering" was actually a BUG (sends all 1201 transactions)

**Key Insight**: When you're close (0.733 score), SMALL changes are better than big rewrites.

### Lesson 2: Base Matters More Than Fix

**opt16 failure taught us**:
```
Correct Fix + Wrong Base = Disaster
Null Semantics Fix + opt11 Base = 20x worse!

Correct Fix + Correct Base = Success?
Null Semantics Fix + opt3 Base = opt17 (testing...)
```

### Lesson 3: Trace Analysis is Critical

Without reading traces, we would never have known:
- opt3: 12 transactions
- opt11: 1201 transactions (100x too many!)
- opt16: Still 1201 transactions

**Variance alone couldn't tell us this** - we needed to dig into actual execution.

### Lesson 4: "Improvements" Can Make Things Worse

**opt11's "fix"** (entity filtering):
- Seemed logical: "Filter by merchant from Phase 1"
- Actually broke it: Sent ALL merchant transactions instead of subset
- Made opt10's -0.798 permanent

**This happens when you don't understand the original approach.**

## The Correct Approach (opt3 Method)

### How opt3 Works

**Phase 5**: Extract relevant subset
- Filters by time (January 2023)
- Filters by merchant (Belles_cookbook_store)
- **Also filters by fee criteria** (transactions that could use fee 384)
- Results: ~12 transactions

**Phase 6**: Apply domain rules
- Enriches transactions with fee matching logic
- Identifies which fee applies to each transaction

**Phase 7**: Compute delta
- For each transaction, calculate fee_old and fee_new
- Sum the deltas
- Return: -0.948 EUR (only 0.008 EUR off!)

### What opt3 Was Missing

**Null semantics** in fee matching:
```python
# opt3 logic (generated by LLM):
if transaction['aci'] in fee_rule['aci']:  # ['C', 'B']
    # Matches

# Problem: If transaction aci=None
None in ['C', 'B'] → False  # Rejects the match!

# Missing 2 transactions where aci=None
```

### The opt17 Fix

**Add guidance in Phase 7 docstring**:
```python
# **NULL SEMANTICS**: Missing transaction field = matches any rule
if txn.get('aci') is None:
    return True  # ← The fix!
```

**Expected result**:
- 12 transactions (aci in ['C', 'B'])
- +2 transactions (aci=None)
- = 14 transactions total
- Delta: -0.94 EUR (exact!)

## Why This Is Hard

### Problem 1: Too Many Variables

When debugging, we had:
- 8 phases (each could be wrong)
- Multiple data files
- Complex fee-switching logic
- Time-based filtering
- Null semantics
- Field name variations

**Solution**: Variance analysis + passing task analysis narrowed it down.

### Problem 2: Misleading "Improvements"

opt11 SEEMED better:
- "Apply entity constraints from Phase 1"
- Explicit merchant filtering
- Clear docstring guidance

But actually made it worse!

**Solution**: Compare to baseline (opt3), not just previous iteration.

### Problem 3: Non-Monotonic Progress

```
opt3: 0.733 (close!)
opt8: 0.733 (sign flip internally, but fixed)
opt9: 0.000 (broke completely)
opt10: 0.182 (recovered but wrong approach)
opt11: 0.182 (same)
opt16: 0.600 (different wrong)
```

Progress wasn't linear - we went backwards multiple times.

**Solution**: Track ALL variants, not just latest. Variance analysis revealed opt3 was best base.

## Decision Points

### Decision 1: Which Base to Use?

**Options**:
- opt11 (latest, most "improvements")

**We chose**: opt3 ✅
**Reasoning**: Score (0.733) beats everything else

### Decision 2: What to Fix?

**Options**:
- Fee-switching algorithm
- Rounding precision
- Transaction subset selection
- Null semantics

**We chose**: Null semantics ✅
**Reasoning**: Passing task analysis said "missing 2 transactions"

### Decision 3: How to Apply Fix?

**Options**:
- Add helper methods (like opt8-opt11)
- Modify Phase 5 filtering
- Add docstring guidance

**We chose**: Docstring guidance ✅
**Reasoning**: opt3 uses ellipsis approach, LLM generates code
