# Prefill System Design

## Overview

**Prefill** is a mechanism that executes code before the LLM begins generating. It primes the generation context with useful information, helping the LLM make better decisions from its first turn.

Prefill code runs as a synthetic "turn zero" — its outputs appear in the conversation history as if the LLM had already executed them, and any variables it defines persist for subsequent LLM-generated code.

## Motivation

Without prefill, the LLM must:
1. Read the task description
2. Guess at the shape/content of inputs
3. Generate exploratory code to understand the data
4. Only then start on the actual task

This leads to wasted iterations and context window. Prefill front-loads exploration so the LLM can see input shapes and values immediately.

**Example without prefill:**
```
Turn 1: LLM generates `print(type(data), len(data))`
Turn 2: LLM generates `print(data[:5])`
Turn 3: LLM finally understands inputs and starts real work
```

**Example with prefill:**
```
Turn 0 (prefill): Auto-shows `data (list): ['item1', 'item2', ...]`
Turn 1: LLM immediately starts real work with full context
```

## Types of Prefill

### 1. Auto-Generated Prefill (InspectInputsPrefill)

The system automatically generates code to inspect method parameters:

```
Call: async def analyze(self, data: list[str], threshold: float) -> Result

data (list):
['item1', 'item2', 'item3', ...]

threshold (float):
0.85

Return type: Result { score: float, items: list[str] }
```

**Design decisions:**
- **Always enabled** for CodeActStrategy — no configuration needed
- **Truncation** — large parameters are truncated to avoid overwhelming context
- **Type hints shown** — return type structure is displayed to guide output format

### 2. User-Defined Prefill (Pre-Ellipsis Code)

Developers can write setup code that runs before LLM generation:

```python
async def analyze(self, data: list[str]) -> Result:
    """Analyze the data."""
    # This code runs in prefill (before LLM generates):
    validated = [x.strip() for x in data if x]
    config = load_analysis_config()
    ...  # LLM generates from here
```

**Design decisions:**
- **Syntax: code before `...`** — reuses Python syntax, no new decorators
- **Variables persist** — `validated` and `config` are available to LLM-generated code
- **Runs once per call** — prefill executes when the method is invoked, not at class definition
- **Full async support** — `await` works naturally since all generation methods are async

## Execution Model

```
┌─────────────────────────────────────────────────────────┐
│                    Method Invocation                     │
└─────────────────────────────────────────────────────────┘
                            │
                            ▼
┌─────────────────────────────────────────────────────────┐
│                   PREFILL PHASE                          │
│  ┌───────────────────────────────────────────────────┐  │
│  │ 1. Auto-generated code (InspectInputsPrefill)     │  │
│  │    - Prints parameter types and values             │  │
│  │    - Shows return type structure                   │  │
│  └───────────────────────────────────────────────────┘  │
│  ┌───────────────────────────────────────────────────┐  │
│  │ 2. User-defined code (if any pre-ellipsis code)   │  │
│  │    - Extracted from method body                    │  │
│  │    - Processes/transforms the inputs               │  │
│  │    - Variables captured to session_locals          │  │
│  └───────────────────────────────────────────────────┘  │
│                                                          │
│  Prefill output added to history as synthetic turn       │
└─────────────────────────────────────────────────────────┘
                            │
                            ▼
┌─────────────────────────────────────────────────────────┐
│                  GENERATION LOOP                         │
│  LLM sees prefill output in history                      │
│  LLM generates code / reasoning / final result           │
│  Session_locals from prefill are available               │
└─────────────────────────────────────────────────────────┘
```

## Key Design Decisions

### Why code before `...` instead of a decorator?

| Option | Pros | Cons |
|--------|------|------|
| `@prefill` decorator on separate method | Explicit, clear separation | Boilerplate, naming conventions |
| String in decorator `prefill="code"` | Explicit | No IDE support, string-based |
| **Code before `...`** | Pythonic, IDE support, concise | None significant |

**Decision:** Code before `...` was chosen for developer ergonomics — it looks like natural Python and gets full IDE support (autocomplete, type checking).

**Note:** In nemo_oo_agents, `...` is the canonical marker for "this is a generation method" — a method whose body is generated by an LLM rather than executed directly by Python. This is a core framework concept, so the syntax is immediately recognizable to nemo_oo_agents developers.

### Why always-on auto-prefill for CodeActStrategy?

Early experiments showed LLMs consistently waste 1-2 turns exploring inputs. Auto-prefill eliminates this overhead for all tasks with no configuration burden.

**Decision:** Make prefill opt-out impossible — it's always beneficial.

### Why combine user and auto prefill?

User-defined prefill handles domain-specific setup (validation, config loading, preprocessing). Auto-prefill handles mechanical inspection (parameter printing). Both are valuable; they're complementary, not alternatives.

**Decision:** Run auto-prefill first to show raw inputs, then user code to process them. This creates a clear narrative: "Here's what you received → Now I'll process it."

### Why persist variables to session_locals?

Prefill would be useless if its work disappeared. The LLM needs to use `validated` and `config` in subsequent turns.

**Decision:** All variables defined in prefill become part of the session namespace, accessible throughout generation.

## Usage Guidelines

### When to use pre-ellipsis code

**Good uses:**
- Data validation and normalization
- Loading configuration
- Computing derived values the LLM will need
- Setting up helper objects

**Avoid:**
- Complex logic (defeats the purpose of LLM generation)
- Side effects that shouldn't repeat
- Code that depends on LLM decisions

### Example patterns

**Validation:**
```python
async def process(self, items: list[dict]) -> Summary:
    """Process items."""
    valid_items = [i for i in items if i.get("status") == "active"]
    ...
```

**Async data loading:**
```python
async def analyze(self, user_id: str) -> Analysis:
    """Analyze user data."""
    user = await self.db.fetch_user(user_id)
    history = await self.db.fetch_history(user_id, limit=100)
    ...
```

**Configuration:**
```python
async def analyze(self, text: str) -> Analysis:
    """Analyze text."""
    model = load_model("sentiment-v2")
    thresholds = get_thresholds_for_domain("finance")
    ...
```

**Preprocessing:**
```python
async def transform(self, data: pd.DataFrame) -> pd.DataFrame:
    """Transform dataframe."""
    data = data.dropna()
    data["date"] = pd.to_datetime(data["date"])
    ...
```

## Observability

Prefill execution is fully traced. All prefill events include `metadata={"prefill": True}`:
- **ToolCallEvent** — the prefill code being executed
- **ToolResultEvent** — execution status
- **ExecutePythonEvent** — output and captured values

This allows trace viewers to distinguish prefill turns from LLM-generated turns.

## Limitations

1. **Comments not preserved** — pre-ellipsis code is extracted via AST; comments are lost in the extracted code (though the original source is preserved in the method definition)
2. **Must be pure setup** — avoid code that depends on LLM decisions (the LLM hasn't run yet)

## Future Considerations

- **Conditional prefill** — skip auto-prefill for simple cases where parameters are trivial
- **IDE integration** — enhanced syntax highlighting for nemo_oo_agents generation methods
