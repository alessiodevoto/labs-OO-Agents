**Towards End-to-End Agent Optimization**

We are building an end-to-end agent optimization system where every part of the agent (orchestration, context engineering, tool design) is optimized based on evaluation results. We've achieved the following results in the last three weeks:

**1\. Benchmark Onboarding**

We've onboarded TauBench, SWEBench, and DABStep. We're approaching (not beating) top leaderboard results using Agent006 without optimization using frontier models. This is evidence that models understand the basics of how to operate as objects within a Python runtime. For more information about the Agent006 runtime which implemented the Agent-as-Object paradigm, see [our code repo](https://gitlab-master.nvidia.com/interactive-agents/nemo_oo_agents).

We prototyped the end-to-end optimizer using Claude Code to analyze traces and rewrite agent code based on feedback. Minimal human feedback was given during initial optimization (initial architectures to choose from), and then a loop running the benchmarks, checking against the answers in the training set, compiling a set of training set solutions, then rewriting the agent based on that analysis.

**3\. Agentic Root Cause Analysis (ARCA)**

We built two complementary tools for understanding agent behavior:

* **Trace Explorer**: A tool for agents to navigate traces, from the overview to the full context window for each call. We used the patterns from [this Anthropic blogpost](https://www.anthropic.com/engineering/writing-tools-for-agents) to create a tool that allows progressive disclosure of trace information from the overview to the full context window of each LLM call.
* **Trace Analyzer Agent**: An agent built with our [Agent006 library](https://gitlab-master.nvidia.com/interactive-agents/nemo_oo_agents) that reads traces and produces a root cause analysis report. This currently runs with Claude Sonnet but we are building an evaluation set to optimize it for Nemotron Nano v3.

**4\. SWE-bench ARCA Results**

Ran the trace analyzer on **70 failed SWE-bench traces** (70 Claude Sonnet 4). The agent automatically clustered failures into 5 categories:

| Failure Mode | % | Description | Hypothesis |
| :---- | :---- | :---- | :---- |
| Implementation Errors | 25.7% | Correct diagnosis but wrong execution (wrong layer/file/approach) | Lack of architectural understanding, best practices |
| Wrong Solution Strategy | 15.7% | Fundamental strategic mistakes made early (turns 20-60) | Lack of strategic reasoning/planning |
| Failed to Execute/Submit | 12.9% | Analysis paralysis, never transitioned to implementation | Context window limitations causing goal loss |
| Missing Context | 11.4% | Didn't read test files or issue descriptions before implementing | Eager implementation bias; lacks enforced pre-implementation requirements gathering phase |
| Pattern Recognition Failures | 8.6% | Missed obvious patterns in codebase despite viewing them | Plan execution blindness; follows pre-formed solutions from general knowledge rather than adapting to local codebase patterns |

These categories directly inform what to fix next: implementation errors → better architectural guidance; wrong strategy → planning phase; missing context → enforced requirements gathering and validation.

**5\. Agent006 Agentic Memory Foundations**

We are landing the final runtime pieces that will allow us to experiment with Agentic memory. When this set of MRs lands, we will have a complete set of context management APIs for developers and agents: history summarization, and Letta-like context blocks.

**ARCA with the Trace Analyzer Agent**

Our agent proceeds in three steps:

- The RulesLawyer subagent finds relevant rules that apply to the question.
- The main agent implements the solution
- The SolutionVerfier agent checks the solution and accepts or rejects it. Upon rejection, the solution is retried.

In this case the RulesLawyer found the right rule which was then promptly ignored by the other agents.

The Trace Analyzer with Nemotron Nano was fast, but it didn’t find the root cause. Instead, it got distracted by the RulesLawyer during tool calling:

**Full Trace Analyzer Output**

Claude Sonnet 4.5

Executive Summary

The agent failed due to domain\_misunderstanding: Agent misunderstood the semantics of null/None for boolean fields in the fee rules domain. The is\_credit field documentation didn't explicitly connect to the null\_field\_rule, leading to confusion about whether is\_credit=null should be included for credit transactions. Expected: 0.120132, Got: 0.117667

Outcome: `FAILURE`

What Went Wrong

Agent filtered for `is_credit == True` only, excluding 21 fee rules with `is_credit == null`. This caused the average to be calculated over 123 fees instead of 144 fees, resulting in 0.117667 instead of the correct 0.120132.

Why It Happened

The agent misunderstood how the null\_field\_rule applies to the boolean is\_credit field. While the system prompt stated 'Null/\[\] \= applies to all' and provided self.applies\_to\_all() helper, the is\_credit\_field documentation only said 'bool. True if the rule applies for credit transactions' without explicitly mentioning that null also applies. The agent interpreted this literally as needing exact boolean True, missing that null (None) means 'applies to both credit and debit'.

Root Cause

`domain_misunderstanding` \- Agent misunderstood the semantics of null/None for boolean fields in the fee rules domain. The is\_credit field documentation didn't explicitly connect to the null\_field\_rule, leading to confusion about whether is\_credit=null should be included for credit transactions.

Key Decision Points

Analysis Notes

This is a domain understanding issue, not a prompt clarity or tool misuse issue. The agent had all the information needed (null\_field\_rule, applies\_to\_all helper) but failed to connect the general null semantics to the specific is\_credit field. The inconsistency in documentation style (list fields explicitly mentioned null, bool field did not) likely contributed to the confusion.
