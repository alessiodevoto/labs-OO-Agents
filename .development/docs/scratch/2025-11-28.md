**Mission:** Reliable and cheap agents that actually solve real-world tasks and learn on the job.
**Approach**: Building Vibe Agents – Agents that are objects within a Python runtime with minimal APIs for orchestration, memory, and task management. ([Vibe agents in 4 slides](https://docs.google.com/presentation/d/13FEUF3fz8Ik7LM8aWqRRIHaCVBIhoKU29oNfvxI8GE4))

**Latest Results:**

- Developed our v2 runtime, Agent006, which manages the Agent/Python interaction including tool and subagent orchestration.
  - Test out [this IPython notebook](https://gitlab-master.nvidia.com/pfurgale/agent-proto-006/-/blob/main/nemo_oo_agents-src/playground/agent_experiments.ipynb?ref_type=heads) which demonstrates the runtime and developer experience (sample multi-agent system listing below).
  - **What works**: great syntax for building and orchestrating multi agent systems. OTel-based tracing with a custom trace viewer. Block-based context management.
  - **What doesn’t work**: Agents asked to write Python sometimes forget they know things, writing brittle code instead of outputting the answer. The standard tool-calling interface adds overhead.
- Agreed to converge prototypes with [Pascal Berard CH](mailto:pberard@nvidia.com), [Christian Schueller CH](mailto:cschueller@nvidia.com), [Severin Klingler CH](mailto:sklingler@nvidia.com) and  team. Targeting parity Wednesday next week.
- Ran a “design by committee” experiment to see which interface LLMs believe will be most effective ([results](https://docs.google.com/document/d/1na2yvCZI1Kn6cvWtZOY6zkVDLN2IfgBiKN8Ikw9AUY4/edit?tab=t.0)). Summary: The consensus among 15 LLMs recommends a pure python interface.
- We implemented an initial evaluation to test inference strategies and ensure the agent does not over-engineer by generating code for tasks that it should know how to reply (e.g., “what is the sentiment of this sentence”), or under-engineer by eagerly replying without producing code (e.g., “how many rs are in strawberry”), that we will use for comparisons of prompts/models/structured output.

**Blockers/slowdowns**

We hit several bugs with our public inference endpoint that [Hayden Wolff US](mailto:hwolff@nvidia.com) reported on their [list](https://docs.google.com/document/d/11-z4wfthbG4hrXg7KepEb1oaLDTEe1o7IXR5jMJiSD8/edit?tab=t.0#heading=h.t45t2gkm1vlm) of issues from GTC DC, which significantly slowed our tests. We have unblocked ourselves by changing to [internal endpoints](https://inference.nvidia.com/) (thanks [Alex Steiner US](mailto:asteiner@nvidia.com)) and changing models away from nemo, but it would be good to fix this for our customers:

- Request to separate reasoning output from final answer with Nemotron models [https://nvbugspro.nvidia.com/bug/5660919](https://nvbugspro.nvidia.com/bug/5660919)
- Possibly related bug: Inconsistent reasoning parsers for NIM models [https://nvbugspro.nvidia.com/bug/5636429](https://nvbugspro.nvidia.com/bug/5636429)
- Request to toggle reasoning via API, rather than system prompt [https://nvbugspro.nvidia.com/bug/5660893](https://nvbugspro.nvidia.com/bug/5660893)
- Build and HF pages have outdated instructions on toggling reasoning mode [https://nvbugspro.nvidia.com/bug/5660843](https://nvbugspro.nvidia.com/bug/5660843)

**Design by committee, recommendation: Explicit Python**

```py
# LLMs produce code that satisfies a strongly typed signature
def strongly_typed_method(self, arg1, arg2) -> int:
  """The docstring contains the method prompt"""

  self.reasoning("The LLM puts chain-of-thought reasoning in reasoning calls")
  self.message("User messages are explicit calls")
  # Eventually the strongly-typed return value is returned, ending the generation session
  return 42
```
