\title{NeMo OO Agents:\\Object-Oriented Harnesses for Reliable AI Agents}

\author{Paul Furgale, Severin Klingler, James Nolan, Matt Staats, Gaia Di Lorenzo, Elisa Martinez Abad, Christian Schueler, Ricardo Silveira Cabral}

\begin{document}

\begin{abstract}
We present NeMo OO Agents, a Python framework for building reliable AI agents by
making the agent a Python object embedded in an auditable harness. Its classes
define state and scope, its methods define capabilities, and its type
annotations define contracts; generation methods cross into LLM execution while
ordinary Python methods remain deterministic helpers. This unifies prompt
engineering with software engineering: behavior can be tested, traced,
versioned, refactored, and optimized in the same object model developers already
use.

We make four contributions.
%
(1)~We introduce an \textbf{object-oriented agent programming model} where
method signatures, docstrings, return types, and visibility constrain the underlying LLM.
%
(2)~We describe the \textbf{harness layer} around the model: pass-by-reference
Python values, object state, context blocks, event history, queues, background
jobs, hot-reloadable skills, trace/eval viewing, and Agent Mesh coordination.
%
(3)~We demonstrate empirically that \textbf{helpers beat prompts}: deterministic
logic expressed as typed Python methods improves reliability on rule-heavy agent
tasks, including DABStep and $\tau$-bench case studies. We report \textbf{full-benchmark evaluations} across Terminal
Bench and SWE-bench Verified, showing these ideas make better use of the underlying models than traditionalharness designs.
%
(4)~We show how the same traces, skills, and queues support a
\textbf{self-evolving harness}: agents can diagnose failures, edit and hot reload
skills, coordinate over a mesh, and launch monitored evaluation campaigns.
\end{abstract}

\section{Introduction}
\label{sec:intro}
% ===========================================================================

Building reliable AI agents remains
difficult~\cite{anthropic2024effectiveagents,anthropic2025longrunningharnesses,anthropic2025multiagent}.
We identify three recurring obstacles in how agents are built today.

\paragraph{Prompts are divorced from code.} Current frameworks such as
LangChain~\cite{langchain2023} and LlamaIndex~\cite{llamaindex2023} separate
prompt templates from application code, creating an impedance mismatch: the
prompt is where behavior is defined, but the code where that behavior is tested,
versioned, and optimized is relegated to a second plane. This separation makes
end-to-end iteration slow and error-prone---a change to a prompt may break
downstream expectations that only surface at runtime.

\paragraph{Iteration recomputes everything.} The cost is sharpest in multi-step
agents, where the natural development loop is to tweak one phase and re-run.
Because efficient LLM serving relies on prefix KV-caching, a change near the top
of a long prompt invalidates the cache for everything that follows, so each edit
forces a full, expensive recomputation---even of the steps that did not change.
What we want instead is to decompose a workflow into phases, freeze the outputs of
the phases we are not editing, and iterate on a single downstream phase while
\emph{replaying} the frozen results of the phases before it.

\paragraph{The wrong tool for each subtask.} Agents routinely ask an LLM to do
work that ordinary code does more reliably and cheaply---counting the letters in
a word, summing a column, enforcing a business rule---while the same systems make
it awkward to drop back to code for the parts that are genuinely deterministic.
Conversely, LLMs excel at subtasks that are hard to express as code, such as
judging the sentiment of a sentence. Most frameworks leave this boundary
implicit, so developers cannot cleanly choose the appropriate execution mode for
each subtask.

NeMo OO Agents addresses all three obstacles by collapsing the prompt/code divide
into a single artifact. We observe that the object-oriented programming model
already provides the abstractions needed for agent construction:

\begin{itemize}
  \item \textbf{Classes} define scope and encapsulation---an agent's state and
        capabilities are co-located.
  \item \textbf{Methods} define capabilities---each method is a distinct,
        testable unit of behavior.
  \item \textbf{Type annotations} define contracts---return types constrain
        what the LLM must produce.
  \item \textbf{Docstrings} define intent---they already serve as natural-language
        descriptions of what a method does.
\end{itemize}

These abstractions are not specific to any one language; the same mapping holds
in any object-oriented language. We implement NeMo OO Agents in Python for a
deliberate reason that is central to this paper's thesis: Python is heavily
represented in the training corpora of modern code-capable LLMs, so the model
already \emph{understands} idiomatic classes, methods, type annotations, and
docstrings without additional training. By keeping the agent-facing surface
in-distribution---ordinary code the model has seen millions of examples of---we
avoid teaching the model a bespoke harness DSL or prompt format. Frameworks that
introduce out-of-distribution abstractions must fight the model's priors; we ride
them. A practical consequence is that improvements to the underlying model
transfer for free: as base models get better at reading and writing Python, they
get better at our agents without any retraining, fine-tuning, or harness-specific
adaptation.

NeMo OO Agents exploits this observation. A method whose body is \texttt{...}
(ellipsis) is implemented by an LLM at runtime; a method with a real body
executes as regular Python. The docstring \emph{is} the prompt. The return type
\emph{is} the contract. The class's other methods \emph{are} the tools the LLM
can call. No separate tool registration, prompt template system, or schema
definition is needed. A complete agent is just a class:

\begin{lstlisting}
class SupportAgent(Agent, llm=llm):
    # Ordinary Python: deterministic, testable, callable as a tool.
    def lookup_order(self, order_id: str) -> Order:
        return DB.get_order(order_id)

    # LLM generation: the `...` body is filled in by the model at
    # runtime; the docstring is the prompt and `Ticket` is the contract.
    async def triage(self, message: str) -> Ticket:
        """Triage the customer {message}. Call self.lookup_order()
        if it refers to an existing order."""
        ...
\end{lstlisting}

There is nothing to learn here that is not already Python. A developer reads this
class and immediately knows what it does---\texttt{lookup\_order} is a normal
method, \texttt{triage} is a method the model implements---without studying a new
framework's vocabulary of chains, nodes, runnables, or prompt templates. The same
is true for the model: because the class is ordinary, in-distribution code, the
model can read it, call \texttt{triage}, extend \texttt{SupportAgent} with a new
method, or write a brand-new agent from scratch as fluently as it writes any other
Python. The single artifact is legible to both audiences at once---humans edit it
as code, and models both \emph{consume} it (as the agent's runtime interface) and
\emph{produce} it (when generating or modifying agents). This dual legibility is
what lets the harness improve as base models improve, with no framework-specific
adaptation on either side.

This single artifact resolves the three obstacles directly. Prompt and code are
no longer divorced: the class \emph{is} the prompt, the contract, and the tested,
versioned, refactorable code, so agent development becomes ordinary Python-native
software engineering in which object-oriented APIs, executable helpers, traces,
and evaluation gates make behavior inspectable and improvable. The execution-mode
boundary becomes explicit and local---an ellipsis body delegates a subtask to the
model, a real body keeps it in deterministic code, and that choice lives in the
method where it belongs. And because each phase is just a method call with typed
inputs and outputs, prior phases can be replayed from stored results, so iteration
cost scales with the phase under development rather than with the whole pipeline.

The rest of the paper is structured as follows.


\paragraph{Related work.} We position NeMo OO Agents against agent frameworks,
code-generating agents, memory systems, and optimization frameworks.

\paragraph{Harness, ideas, and contributions.} We explain the programming model
and harness: typed methods, CodeAct/Predict boundaries, pass-by-reference Python
values, object state, context/events, queues, skills, trace viewing, capability
tests, case studies, and qualitative harness behavior.

\paragraph{Experimental results.} We report benchmark results on
Terminal Bench and SWE-bench Verified.

\section{Related Work}
\label{sec:related}
% ===========================================================================

\paragraph{Agent frameworks.}
LangChain~\cite{langchain2023} and LlamaIndex~\cite{llamaindex2023} provide
tool-use abstractions but separate prompt templates from application logic.
AutoGen~\cite{wu2023autogen} and CrewAI~\cite{crewai2024} focus on multi-agent
conversation patterns. DSPy~\cite{khattab2023dspy} introduces programmatic
optimization of LLM pipelines via signatures and teleprompters. NeMo OO Agents shares
DSPy's optimization philosophy but uses standard Python OOP as the abstraction
layer and treats deterministic code as a first-class optimization lever.

\paragraph{Practitioner agent engineering.}
Anthropic engineering guidance emphasizes workflows and agents, tool design,
context engineering, long-running harnesses, MCP-based tool integration, code
execution, computer use, and multi-agent systems~\cite{anthropic2024effectiveagents,anthropic2025tools,anthropic2025contextengineering,anthropic2025longrunningharnesses,anthropic2024mcp,anthropic2025codeexecutionmcp,anthropic2025advancedtooluse,anthropic2024computeruse,anthropic2025multiagent}.
This literature is operational rather than benchmark-driven, but it motivates
the same design pressure as NeMo OO Agents: agent reliability depends on the
harness surrounding the model, including tool interfaces, context management,
execution sandboxes, and observable long-running workflows.
\paragraph{Code-generating agents and recursive harnesses.}
SWE-Agent~\cite{yang2024sweagent} and OpenHands~\cite{openhands2024} build
agents for software engineering tasks. CodeAct~\cite{wang2024codeact} proposes
code execution as the primary action modality. Recent survey work frames the same
shift more broadly as \emph{code as agent harness}~\cite{ning2026codeharness}:
code becomes the substrate for reasoning, acting, environment modeling,
execution-based verification, memory, tool use, and multi-agent coordination.
Recursive Language Models~\cite{zhang2025recursive} show that models can
extend context processing by recursively decomposing prompts and invoking
subcalls over snippets. Recursive Agent Harnesses~\cite{lumer2026recursive}
extend this recursion from model calls to full harness instances with filesystem
access, code execution, planning, and parallel subagent work. NeMo OO Agents is
complementary to these views but makes the harness concrete as an
object-oriented Python runtime where the agent's own methods are the available
tools.

\paragraph{Memory architectures.}
Letta/MemGPT~\cite{packer2023memgpt} introduces OS-inspired memory management for
LLMs with a tiered memory hierarchy.
Reflexion~\cite{shinn2023reflexion} uses verbal self-reflection as a form of
episodic memory. RAG~\cite{lewis2020rag} retrieves from external knowledge
stores. NeMo OO Agents' memory architecture differs in providing structured,
per-agent-instance memory (event history, context blocks, summarization) rather
than a shared retrieval store.

\section{Harness, Ideas, and Contributions}
\label{sec:harness-contributions}
% ==========================================================================

Most agent harnesses still make the model work through the same interface:
an OpenAI-style transcript of system, user, assistant, and tool messages, plus
a list of tools the assistant is allowed to call.  That interface is useful,
but it narrows what harness design can be.  Progress becomes a matter of
building better tool schemas, better tool routers, and better message
protocols around the same chat-and-tool-calling loop.  Crucially, this interface
is something we teach models during post-training; it is not already part of the
corpus of training data.

NeMo OO Agents makes a different choice: it makes the model-facing harness look
like ordinary Python.  A NeMo OO agent knows that it is an object in a Python
runtime.  Its class defines what kind of agent it is.  Actions are Python code
and it can call its own methods and common libraries, and orchestrate its own
work or the work of teams of agents.  Its type annotations define the input and
output contracts.  Its instance fields hold the state it has learned while working.
The harness shows this object to the model as its working environment and
records how the model uses it.  Python is therefore not just the implementation
language; it is the interface the model actually sees.

This object boundary unlocks six ideas from the NeMo OO programming model:
\emph{typed methods}, \emph{pass-by-reference}, \emph{code as action},
\emph{loop engineering}, \emph{object state}, and \emph{harness APIs}. None of
the ideas is new in isolation. The contribution is that all six live on the
same object that the model can inspect and act through. Together they turn
agent development from prompt assembly into interface design: developers decide
which capabilities should be deterministic Python, which should be LLM
generation, what state should survive a turn, and what evidence should be left
in the trajectory.

\paragraph{Typed methods.}
Typed methods make an LLM call look like an ordinary Python method call.  The
method signature tells the model what inputs it has, the docstring says what
work to do, and the return annotation gives the harness a contract to validate.
The result is a Python value, not a paragraph that downstream code must parse.

\begin{lstlisting}
class PatchAgent(Agent):
    async def diagnose(self, issue: Issue, trace: Trace) -> FixPlan:
        "Find the root cause of {issue} using {trace}."
        ...

plan: FixPlan = await agent.diagnose(issue, trace)
assert plan.files_to_edit
\end{lstlisting}


\paragraph{Pass-by-reference.}
Pass-by-reference means the model can work with live Python objects instead of
forcing every value through a JSON or text serialization boundary.  In the
Agent006 intro demo, the predecessor to NeMo OO, an agent receives raw 3-D
assets: a \texttt{trimesh.Trimesh}, a \texttt{trimesh.PointCloud}, and a
\texttt{Path} to a \texttt{.glb} asset.  The model sees names, types, and bounded
previews, then writes Python against the real objects.

\begin{lstlisting}
class PlotlyVisualizer(Agent):
    """Visualizes 3D data with Plotly."""

    async def show(self, items: dict[str, Any]) -> str:
        """Visualize all items in one Plotly figure, laid out side by side.
        Each value may be a trimesh mesh, point cloud, Path, bytes, or dict."""
        ...

data_dir = Path("data")
objects = {
    "bunny": trimesh.load(data_dir / "bunny.obj"),
    "city_scan": trimesh.load(data_dir / "city_scan.ply"),
    "duck": data_dir / "duck.glb",  # Path: agent must load it
}
await PlotlyVisualizer().show(objects)
\end{lstlisting}

The first prefill turn shows the live arguments without serializing the full
mesh, point cloud, or asset file.  Loading the Agent006 MR~498 example data
produces this preview:

\begin{lstlisting}

{

    'city_scan': <trimesh.PointCloud(vertices.shape=(21000, 3))>,
    'duck': PosixPath('data/duck.glb'),
}

Return type: str
\end{lstlisting}

\paragraph{Code as action.}
Code as action means the model acts by writing Python, not only by selecting one
JSON tool call at a time.  The action can use variables, loops, conditionals,
ordinary libraries, and methods on \texttt{self}; the harness executes the cell
and returns the results to the model.  A CodeAct cell can recursively call
generation methods, create and await subagents, define helper functions, and 
read/write object state.

\begin{lstlisting}
# Model-written action inside a CodeAct strategy.
pages = await self.pdf.pages("manual.pdf")
ocr_agent = PageOCRAgent()

async def read_page(page: PDFPage) -> PageText:
    text = await ocr_agent.ocr(page)
    return PageText(page=page.number, text=text)

page_texts = await asyncio.gather(*(read_page(page) for page in pages))
return_result(page_texts)
\end{lstlisting}

\paragraph{Loop engineering.}
There is no separate workflow DSL and no fork between
``workflow'' and ``ReAct'' programming.  The mental model for all execution is
Python.  Developers and agents freely interleave deterministic code, generation
methods, CodeAct cells, and subagent calls inside the same control flow.

\begin{lstlisting}
async def ocr_document(self, pdf: PDF) -> DocumentText:
    pages = await self.split_pages(pdf)        # deterministic helper
    worker = PageOCRAgent()                    # agent loop as an object
    texts = []
    for batch in batched(pages, 8):
        texts.extend(await asyncio.gather(
            *(worker.ocr(page) for page in batch)  # generation method calls
        ))
    return await self.merge_pages(texts)       # another typed method
\end{lstlisting}

\paragraph{Object state.}
The agent has explicit state it can store, inspect, and reuse
later.  Short-lived Python variables handle the current turn; durable fields assigned to \texttt{self} survive turns, summaries, and restarts; task-specific state can
live on ToDo objects.  The model does not have to reconstruct all progress from a
message transcript.

\begin{lstlisting}
self.failing_tests = ["test_parser", "test_roundtrip"]
self.current_hypothesis = "schema cache is stale"

todo = self.todo.add("Fix schema cache invalidation")
todo.files = ["parser/cache.py", "tests/test_cache.py"]
\end{lstlisting}

\paragraph{Agent-Visible Harness APIs.}
Harness APIs cover model-visible access to the harness context and event
stream.  We focus on three surfaces: structured context blocks in the style of
Letta/MemGPT memory sections, per-turn dynamic context computed from live state,
and events that let the agent inspect what happened in the session.  Dynamic
context also covers runtime assembly such as skill/tool inventory blocks or
summaries derived from event history.  We distinguish developer APIs from agent
APIs.  Many harnesses let developers assemble prompts, memory, or callbacks
before a run.  NeMo OO Agents exposes the same kind of control plane to the
model as ordinary Python: the agent can add or refresh context blocks, define
dynamic context, and inspect events while it is working.

\begin{lstlisting}
self.context.set("goal", "Diagnose the schema cache failure")
self.context.set_dynamic("progress", "self.v.current_hypothesis")
self.context.set_dynamic("skills", "self.skills.status()")

for event in self.events.query(regex="schema", limit=5):
    print(event.tag, event.summary)
\end{lstlisting}

\subsection{Agents as Python Objects}
\label{sec:model}
% ---------------------------------------------------------------------------

A NeMo OO agent is a Python class.  Methods with ordinary Python bodies execute
deterministically.  Methods whose body is the ellipsis literal
(\texttt{...}) are generation methods: the harness implements them at runtime
using an LLM strategy.  The method docstring becomes the task instruction, the
method arguments become structured inputs, and the return annotation becomes the
output contract.

\begin{lstlisting}
class InventoryAgent(Agent):
    """Agent that checks inventory and explains fulfillment decisions."""

    # Deterministic Python: exact state lookup, cheap and testable.
    def get_stock(self, item: str) -> int:
        return INVENTORY.get(item, 0)

    # LLM generation: semantic judgment over typed inputs and helper methods.
    async def can_fulfill(self, items: list[str]) -> FulfillmentDecision:
        """Check whether we can fulfill {items}.
        Use self.get_stock() for inventory lookups before deciding."""
        ...
\end{lstlisting}

The same object therefore contains both software 1.0 and software 3.0 behavior.
The developer does not separately register tools, duplicate schemas into prompt
strings, or maintain a parallel prompt hierarchy.  Refactoring a helper method,
renaming a field, changing a return type, or adding a test happens in the same
place it would in ordinary Python code.

This object boundary is also the model's interface.  At generation time, the
harness renders an inspectable API for \texttt{self}: visible methods, fields,
type signatures, docstrings, and selected context blocks.  The model can call
methods on \texttt{self}, inspect objects with \texttt{doc(obj)}, and write code
against the live Python objects it was given.  Python is therefore not only the
implementation language, but also the agent interface language.

Visibility is part of that interface design.  Agent members are visible by
default, because the model should know its own capabilities.  Module-level names
are hidden by default, because imports and helper constants are usually
implementation details.  Developers can opt members out with \texttt{@hidden} or
hidden annotations, and can opt module-level names in when they are intended as
agent affordances.

\subsection{Runtime Harness}
\label{sec:harness}
% ---------------------------------------------------------------------------

The object model is only half of NeMo OO Agents.  The other half is the harness:
the event loop around that Python object.  It maintains the conversation with
the model, exposes tools, executes code, validates outputs, records traces, and
decides what context should be visible on each turn.  A single generation method
invocation can include multiple model calls, Python tool calls, observations,
validation failures, retries, and summaries.  All of these are represented as
typed events rather than opaque prompt text.

The main runtime components are:

\begin{itemize}
  \item \textbf{Strategies.}  Each generation method has an execution strategy.
        A simple extraction method can use a single structured-output call,
        while an implementation method can use a CodeAct loop with Python
        execution and observations.  Strategy choice is per method, not per
        agent, so one object can mix cheap routing, semantic classification,
        and expensive iterative coding.
  \item \textbf{Context blocks.}  Agents attach named context to the system
        prompt.  Static blocks pin durable facts; dynamic blocks re-render a
        Python expression each turn; scoped blocks temporarily specialize one
        call.  Context is managed as structured state, not by manual prompt
        concatenation.
  \item \textbf{Events and traces.}  The harness records model messages, tool
        calls, code cells, observations, validation errors, summaries, and final
        returns.  These traces are used for debugging, benchmark analysis,
        regression tests, and trace-informed optimization.
  \item \textbf{Validation.}  Return types, especially Pydantic models, are
        enforced at the harness boundary.  The model may reason in free form
        inside a strategy, but the method returns a typed Python value or fails
        with evidence.
\end{itemize}

This design turns prompting problems into software-interface problems.  A
failure can often be fixed by making an affordance more discoverable, moving an
exact operation into a helper, tightening a type contract, adding a validation
step, or changing a method's strategy.  These are ordinary engineering actions
that can be reviewed, tested, and optimized independently.

% ---------------------------------------------------------------------------
\subsection{Tools, Skills, and Persistent State}
\label{sec:harness:tools}
% ---------------------------------------------------------------------------

NeMo OO agents are not limited to functions declared in one class.  The runtime
mounts object-oriented tool surfaces onto the agent instance.  Examples include
shell and repository tools, session search, trace exploration, web publishing,
model catalogs, evaluation launchers, TODO management, and mesh communication.
These are exposed as Python objects such as \texttt{self.shell},
\texttt{self.repo}, \texttt{self.todo}, and \texttt{self.trace\_explorer}, with
methods and docstrings that the model can inspect at runtime.

Skills extend this mechanism.  A skill is a reusable Python library attached to
the agent as an object.  When an agent discovers a repeatable pattern---for
example, how to mine benchmark traces, run a provider capability matrix, or
prepare a paper evidence table---that pattern can be promoted from an ad hoc
prompt instruction into a versioned Python skill.  Skills make the harness
self-evolving: successful procedures become callable software that future agents
can inspect, test, and reuse.

State is likewise explicit.  Short-lived variables live in the Python execution
session; durable working state is stored on snapshot-backed variables such as
\texttt{self.v}; task-specific state is stored on TODO objects.  Long-running
agents can therefore survive context summarization and session restarts without
relying on the model to remember every detail in its prompt.

% ---------------------------------------------------------------------------
\subsection{Long-Running Work and Coordination}
\label{sec:harness:coordination}
% ---------------------------------------------------------------------------

The harness supports tasks that exceed a single model context window or a single
foreground command.  TODOs provide a visible decomposition of work, dependency
tracking, task-scoped notes, and progress updates.  Queues and background
producers allow long-running commands---for example, benchmark jobs or test
suites---to run asynchronously while the agent remains responsive.  Summarizers
compress old event history when context budgets are reached, preserving the
state needed for the next turn.

NeMo OO also includes coordination primitives.  A parent agent can delegate a
TODO to a fresh subagent with its own context, avoiding contamination between
subtasks.  Mesh channels let multiple named agents collaborate on a shared
project: one agent can edit a paper, another can mine traces, and another can
track external benchmark runs.  The coordination layer is deliberately ordinary
software infrastructure---queues, tasks, event streams, and object references---
rather than an implicit group-chat transcript that every model must parse.

% ---------------------------------------------------------------------------
\subsection{Evaluation and Trace-Informed Improvement}
\label{sec:harness:evaluation}
% ---------------------------------------------------------------------------

The same harness used for interactive work is used for evaluation.  Capability
tests check whether models choose the right execution mode, not only whether
they guess the right answer.  Benchmark runners capture complete trajectories
for SWE-bench, Terminal-Bench, CyberGym, and domain tasks.  Trace viewers and
analysis tools expose where the model used the harness well, where it ignored an
affordance, where it overloaded context, and where a helper or skill would have
removed unnecessary reasoning.

This closes the optimization loop.  Developers inspect traces, identify an
interface failure, change the Python harness, and rerun the same task.  The
improvement may be a new helper, a clearer method contract, a smaller context
surface, a better strategy choice, or a new skill.  In each case the artifact is
software, not just a longer prompt.  The result is a system that can improve
through the same mechanisms as conventional software: decomposition,
instrumentation, regression testing, and refactoring.

\subsection{Helpers, Capability Tests, and Case Studies}
\label{sec:helpers}
% ---------------------------------------------------------------------------

A central finding of our work is that \emph{deterministic helper methods
consistently outperform prompt instructions} for tasks with exact semantics.
We call this the ``helpers beat prompts'' principle.

% ---------------------------------------------------------------------------
\subsubsection{The Right Division of Labor}
\label{sec:helpers:division}
% ---------------------------------------------------------------------------

LLMs excel at semantic tasks (sentiment analysis, summarization, interpretation)
but struggle with precise computation (character counting, rule matching, exact
arithmetic). The ``strawberry problem''---LLMs cannot reliably count the letter
`r' in ``strawberry''---illustrates a broader pattern: any task with an exact
algorithmic solution should be implemented in code, not delegated to the LLM.

\begin{table}[h]
\centering
\caption{When to use helpers vs.\ LLM generation.}
\label{tab:division}
\begin{tabular}{ll}
\toprule
\textbf{Task type} & \textbf{Approach} \\
\midrule
Domain rules with exact semantics & Deterministic helper \\
Fuzzy matching, interpretation & LLM generation \\
Data transformation (known schema) & Deterministic helper \\
Multi-step reasoning & LLM with CodeAct \\
String formatting, parsing & Deterministic helper \\
Classification, routing & LLM (StructuredOutput) \\
\bottomrule
\end{tabular}
\end{table}

In NeMo OO Agents, helpers are regular class methods. Because they appear in
\texttt{doc(self)}, the LLM discovers and calls them naturally---no tool
registration needed.

\subsubsection{Capability Tests: Integration Tests for Agent Runtimes}
\label{sec:helpers:captests}
% ---------------------------------------------------------------------------

A framework like NeMo OO Agents places specific demands on the underlying LLM:
it must write executable Python in a REPL, call \texttt{self.*} methods as tools,
produce structured output conforming to Pydantic types, manage state across
turns, and know when to reason directly versus when to write code. These are
not generic ``reasoning'' abilities---they are integration-level capabilities
that determine whether a model can function inside an agentic runtime.

We introduce \emph{capability tests}: a suite of 33 focused integration tests
that exercise these abilities in isolation. Each test targets a single
capability (e.g., ``can the model call a helper method and use its return
value?'', ``can it iterate in a REPL to refine output?'', ``can it extract
structured data from a large context?'') and is scored on two independent
dimensions:
\begin{enumerate}
  \item \textbf{Output correctness}: did the agent produce the right answer?
  \item \textbf{Method correctness}: did it use the right approach?
\end{enumerate}

This dual scoring catches a critical failure mode: an LLM that writes
\texttt{if "happy" in text: return "positive"}---naive keyword matching---may
produce correct output on simple inputs but uses entirely the wrong method.
Standard benchmarks miss this; capability tests do not.

\paragraph{What is not yet covered.}
The current suite focuses on single-agent capabilities within the CodeAct and
StructuredOutput strategies. Notable gaps include:
\begin{itemize}
  \item \textbf{Multi-agent orchestration}: sub-agent spawning, delegation,
        and result aggregation across agent boundaries.
  \item \textbf{Context block management}: verifying that the LLM correctly
        reads, updates, and reasons over dynamic context blocks across turns.
  \item \textbf{Long-horizon state tracking}: tasks requiring consistent state
        management over 10+ turns with interleaved tool calls.
  \item \textbf{Visibility control compliance}: testing that the LLM respects
        \texttt{@hidden} boundaries and does not attempt to call hidden methods.
\end{itemize}

\paragraph{Frontier tests.}
Beyond coverage gaps, we identify three directions for next-generation
capability tests:
\begin{itemize}
  \item \textbf{Self-correction under type errors}: can the model recover when
        its generated code fails Pydantic validation, without human hints?
  \item \textbf{Strategy-aware mode selection}: given a task that could be
        solved by either StructuredOutput or CodeAct, does the model select the
        more efficient strategy?
  \item \textbf{Helper discovery}: when \texttt{doc(self)} reveals a
        deterministic helper that solves the task exactly, does the model call
        it instead of reimplementing the logic in generated code?
\end{itemize}

\subsection{Compositional Optimization Case Studies}

A key advantage of the agent-as-object model is that it enables
\emph{compositional optimization}: because agents are decomposed into typed

\subsubsection{Case Study: DABStep}
\label{sec:optimization:dabstep}
% ---------------------------------------------------------------------------

DABStep~\cite{dabstep2025} is a data analysis benchmark with 450 tasks requiring
agents to reason over transaction data, fee schedules, and business rules. The
published SOTA at time of writing is 16\% (o3-mini). We achieved \textbf{80\%}
on a 10-task evaluation subset through systematic application of the helpers
beat prompts principle.

\paragraph{Optimization trajectory.} Figure~\ref{fig:dabstep} shows the
progression across 55 optimization iterations:

\begin{itemize}
  \item \textbf{Baseline (opt1, 40\%)}: All logic delegated to the LLM via
        prompt instructions. The LLM inconsistently applied fee matching rules.
  \item \textbf{Architectural fix (opt3, 50\%)}: Trace analysis revealed a
        missing \texttt{data\_dir} parameter---a structural bug, not a prompt
        issue. Fixed in 15 minutes.
  \item \textbf{Progressive helpers (opt4--opt44, 70\%)}: Fee matching, fraud
        rate calculation, and EUR rounding moved from prompts to deterministic
        methods. Each helper eliminated a class of inconsistent errors.
  \item \textbf{Ceiling (opt49, 80\%)}: Final EUR rounding fix. Subsequent
        iterations (opt50--opt55) all regressed---10 of 11 attempts to improve
        further broke previously passing tasks.
\end{itemize}

def fee_matches(self, fee: dict, txn: dict) -> bool:
    """Deterministic fee matching -- not LLM-generated."""
    if fee['card_scheme'] != txn['card_scheme']:
        return False
    if fee.get('is_credit') is not None:
        if fee['is_credit'] != txn['is_credit']:
            return False
    return True

def calc_fee(self, fee: dict, amount: float) -> float:
    return fee['fixed_amount'] + fee['rate'] * amount / 10000
\end{lstlisting}

When fee matching was left to the LLM, it got rules wrong inconsistently---
sometimes treating \texttt{null} as ``no match'' instead of ``matches all,''
sometimes ignoring volume ranges. When implemented as a helper, accuracy jumped
immediately because the logic executes deterministically every time.

\paragraph{Ceiling analysis.} The two remaining failures reveal the limits of
the approach: one task requires ``fee switching'' (recalculating optimal fees
for all transactions under a counterfactual), which is too complex for a simple
helper but too brittle for prompt engineering. The other task's expected answer
appears to be incorrect in the benchmark itself.

\subsubsection{Why Decomposition Enables Optimization}
\label{sec:optimization:why}
% ---------------------------------------------------------------------------

In monolithic agent designs, a single prompt controls all behavior. Improving
one aspect (e.g., making the agent more careful about edge cases) often degrades
another (e.g., making it slower or more verbose on simple cases). This is the
\emph{competing constraints} problem we observed at the DABStep ceiling: 10 of
11 attempts to improve the remaining failures regressed previously passing tasks.

NeMo OO Agents' method-level decomposition breaks this coupling:

\begin{enumerate}
  \item Each method has its own prompt (docstring), strategy, and optionally
        its own LLM.
  \item Optimizing one method's docstring cannot affect another method's behavior
        ---they are separate LLM calls with separate prompts.
  \item The orchestrator (pure Python) guarantees execution order, so
        optimization cannot change the workflow structure.
\end{enumerate}

This is analogous to how modular software is easier to optimize than monolithic
software: you profile, identify the bottleneck, and fix it in isolation.

\subsubsection{Trace-Informed Optimization Loop}
\label{sec:optimization:loop}
% ---------------------------------------------------------------------------

NeMo OO Agents traces all public methods by default, capturing every LLM call, code
execution, and return value. This enables a systematic optimization loop:

\begin{enumerate}
  \item \textbf{Run}: Execute agent on benchmark tasks, collect traces.
  \item \textbf{Diagnose}: Identify which method failed and why (wrong output?
        wrong approach? context missing?).
  \item \textbf{Target}: Apply the fix to the specific method---change its
        docstring, add a helper, switch its strategy.
  \item \textbf{Verify}: Re-run and confirm the fix works without regressing
        other methods.
\end{enumerate}

Because methods are independent LLM calls, step 4 is reliable: fixing
\texttt{compute\_fee()} cannot break \texttt{classify\_intent()}.

\paragraph{Parameterized strategies.} Strategy configurations are Python
dataclasses, enabling programmatic ablation:

\begin{lstlisting}
# Create prompt variant for A/B testing
minimal = CodeActConfig(
    instructions="Output Python code. Define target method.",
    error_empty="Define `{method}`.",
)
strategy = CodeActStrategy(config=minimal)
\end{lstlisting}

\subsection{State, Context, and Trace Memory}
\label{sec:memory}
% ---------------------------------------------------------------------------

NeMo OO Agents currently provides memory through implemented harness mechanisms
rather than through a single monolithic memory module.

\paragraph{Object and snapshot state.} Agent instances hold managers, handles,
configuration, and progress markers as ordinary Python state. Snapshot-backed
stores persist selected values across turns and sessions.

\paragraph{Event history.} Every LLM call, code execution, tool invocation, and
message is recorded as an event. Agents can query and summarize this history,
and the viewer can reconstruct trajectories from spans.

\paragraph{Context blocks.} Static and dynamic context blocks control what is
rendered into the prompt. Dynamic blocks let the agent expose a live projection
of state without stuffing the full state object into every turn.

\paragraph{Session search.} Historical sessions can be indexed and searched,
turning prior traces into a retrieval layer for debugging and resumption.

\paragraph{Future work: Continuous Integration Memory.} The CIM design in
\texttt{paper/cim-draft.md} treats memory as active verification rather than
passive retrieval: topic shards act like a test suite and flag contradictions in
new outputs. We leave CIM in future work until its planned contradiction,
scaling, and context-efficiency experiments are complete.

\subsection{Anecdotal Harness Behavior}
\label{sec:anecdotal}
% ---------------------------------------------------------------------------

Aggregate pass rates are necessary but incomplete: many harness improvements
show up first as qualitative changes in how agents diagnose, coordinate, and
recover during long-running work. The following examples are anecdotal rather
than controlled ablations, but they describe recurring behaviors that motivated
our instrumentation choices.

\paragraph{Self-repair and extension.} In several sessions, agents improved
their own operating environment while continuing the parent task. Mesh and
queue handling were debugged from live traces, patched, reloaded, and then used
for subsequent coordination in the same report-writing workflow. Session search
served a similar role: once prior evaluation artifacts were indexed, an agent
could recover a historical capability-test run and route the exact JSONL output
and session identifier to another analyst instead of re-running the experiment.
These episodes are the practical version of the harness thesis: reusable
behavior moves from one-off prompt instructions into inspectable Python helpers
that can be tested and invoked again.

\paragraph{Infrastructure diagnosis.} Trace evidence repeatedly prevented
benchmark failures from being misread as model-quality failures. Examples
include provider or gateway errors after a passing smoke gate, Docker Hub rate
limits invalidating container setup, missing \texttt{PYTHONPATH} entries for the
agent CLI, and Docker network-pool exhaustion during Terminal Bench runs. In
each case, the useful signal was not merely that a task failed, but where the
failure occurred: before model reasoning, during harness setup, inside tool
execution, or in the scorer path. This separation lets us quarantine invalid
runs instead of tuning prompts against infrastructure noise.

\paragraph{Human/agent coordination.} Mesh channels made the report-writing
process itself inspectable. Multiple agents joined \texttt{\#report-writing},
announced branch ownership, shared trace-analysis slices, and acknowledged when
a section was stable or under edit. The branch discipline used for this draft is
a small but representative example: one contributor edited the introduction
while others continued on non-introduction sections, with each agent fetching,
fast-forwarding, and validating before building on the shared branch.

\paragraph{Harness adapters.} Adapter work for Hermes and PI exposed whether a
benchmark harness was genuinely executing trajectories or only returning
metadata. Installation checks, model-routing smoke tests, and trace availability
were treated as first-class evidence before interpreting pass rates. This is why
we report interim Hermes status separately and defer PI and Terminal-Bench
trajectory claims until artifact grouping/import produces rows with usable
traces.

\subsection{Limitations and Future Work}
\label{sec:discussion}
% ---------------------------------------------------------------------------

\paragraph{Limitations.} Visibility is informational, not enforced---a
determined LLM could guess hidden attribute names. Context blocks and event
history are in-memory only; cross-session persistence requires explicit
serialization. The ``helpers beat prompts'' finding applies most clearly to
rule-based domains; creative or open-ended tasks may not benefit from the same
decomposition.

\paragraph{SFT from agent traces.} NeMo OO Agents' tracing infrastructure captures
complete trajectories suitable for supervised fine-tuning. We have a pipeline
for generating SFT data from SWE-bench trajectories and plan to evaluate whether
fine-tuned smaller models can replicate strong agent behavior.

\paragraph{Broader impact.} By making agent behavior auditable (traces),
decomposable (methods), and type-safe (Pydantic contracts), NeMo OO Agents aims to
make AI agents more predictable and debuggable---properties we believe are
prerequisites for trustworthy deployment.

\section*{Conclusion}
\label{sec:conclusion}
% ===========================================================================

We presented NeMo OO Agents as an object-oriented harness for reliable AI
agents. The central claim is not only that agents can be represented as Python
objects, but that the surrounding harness---state, events, context assembly,
queues, skills, trace storage, and evaluation grouping---is what makes those
objects debuggable and improvable. Helpers beat prompts because deterministic
subproblems belong in typed Python methods. Together these
properties turn agent development from one-off prompt engineering into an
iterative software engineering loop.
